================================================================================
REPS TRACKER BACKEND DEVELOPMENT PLAN
Python-based API for Real Estate Professional Status Hours Tracking
================================================================================

CURRENT STATE ANALYSIS
----------------------
- Frontend: Next.js 14 (App Router), TypeScript, Zustand, Tailwind CSS
- Storage: Browser localStorage (no persistence across devices)
- Auth: None
- Data: HoursEntry, Category, Property entities

GOAL
----
Build a Python backend API to:
- Enable user authentication and multi-device sync
- Persist data in a proper database
- Allow future features (reports, sharing, multi-user)
- Support freemium model (future release)

================================================================================
1. CORE TECHNICAL CHALLENGES
================================================================================

1.1 DATA MIGRATION
------------------
Challenge: Users have existing data in localStorage that must not be lost.
Solution:
  - Implement a one-time migration endpoint POST /api/migrate
  - Frontend detects if user has localStorage data + no server data
  - Bulk upload localStorage entries after first login
  - Mark migration complete to prevent duplicates

1.2 OFFLINE-FIRST SYNC
----------------------
Challenge: App should work offline (current behavior) but sync when online.
Solution:
  - Keep Zustand + localStorage as primary (optimistic UI)
  - Background sync to server when online
  - Conflict resolution: "last write wins" with updatedAt timestamps
  - Queue failed requests for retry

1.3 API LATENCY
---------------
Challenge: Current app is instant (localStorage). Server calls add latency.
Solution:
  - Optimistic updates: UI updates immediately, syncs in background
  - Batch operations: sync multiple changes in single request
  - Use WebSockets or polling for real-time sync (optional, phase 2)

1.4 AUTHENTICATION
------------------
Challenge: Secure user identification without complexity.
Solution:
  - Google OAuth for authentication (MVP)
  - JWT tokens (access + refresh token pattern) issued after Google auth
  - Email/password login deferred to post-MVP

1.5 GOOGLE OAUTH IMPLEMENTATION
-------------------------------

Overview:
  - Use Authorization Code Flow (most secure for web apps)
  - Google handles password security, 2FA, account recovery
  - We only store Google user ID and profile info (no passwords)

Setup Requirements:
  1. Create project in Google Cloud Console
  2. Enable Google+ API / People API
  3. Configure OAuth consent screen
  4. Create OAuth 2.0 credentials (Client ID + Secret)
  5. Set authorized redirect URI: https://yourapp.com/api/auth/google/callback

OAuth Flow:
  ┌─────────────────────────────────────────────────────────────────────────┐
  │ 1. User clicks "Sign in with Google" button on frontend                 │
  │    ↓                                                                    │
  │ 2. Frontend redirects to Google OAuth URL with:                         │
  │    - client_id, redirect_uri, scope (email, profile), state (CSRF)      │
  │    ↓                                                                    │
  │ 3. User authenticates with Google (enters credentials on Google)        │
  │    ↓                                                                    │
  │ 4. Google redirects back to our callback URL with authorization code    │
  │    ↓                                                                    │
  │ 5. Backend exchanges code for access_token + id_token                   │
  │    POST https://oauth2.googleapis.com/token                             │
  │    ↓                                                                    │
  │ 6. Backend extracts user info from id_token (JWT):                      │
  │    - email, name, picture, google_id (sub claim)                        │
  │    ↓                                                                    │
  │ 7. Backend creates/updates user in database                             │
  │    ↓                                                                    │
  │ 8. Backend issues our own JWT tokens (access + refresh)                 │
  │    ↓                                                                    │
  │ 9. Redirect to frontend with tokens (or set httpOnly cookie)            │
  └─────────────────────────────────────────────────────────────────────────┘

User Creation Logic (MVP - Google Only):
  - If Google ID exists → log in existing user
  - If Google ID not found → create new account with Google profile

Frontend Implementation:
  Option A: Redirect Flow (simpler)
    - Button redirects to: /api/auth/google/authorize
    - Backend redirects to Google
    - Callback redirects back to frontend with token

  Option B: Popup Flow (better UX)
    - Use @react-oauth/google package
    - Google popup handles auth
    - Returns credential to frontend
    - Frontend sends credential to backend for verification

Environment Variables Required:
  GOOGLE_CLIENT_ID=your-client-id.apps.googleusercontent.com
  GOOGLE_CLIENT_SECRET=your-client-secret
  GOOGLE_REDIRECT_URI=https://yourapp.com/api/auth/google/callback

3. PRIVACY AND DATA SECURITY
================================================================================

3.1 AUTHENTICATION SECURITY
---------------------------
- Passwords hashed with bcrypt (cost factor 12)
- JWT access tokens: short-lived (15 minutes)
- JWT refresh tokens: longer-lived (7 days), stored in httpOnly cookie
- Refresh tokens stored hashed in database (revocable)
- Rate limiting on auth endpoints (5 attempts per minute)

3.2 DATA PROTECTION
-------------------
- All API endpoints require authentication (except auth routes)
- Users can only access their own data (user_id filter on all queries)
- Input validation on all endpoints (Pydantic models)
- SQL injection prevention via ORM (SQLAlchemy)
- XSS prevention: API returns JSON only, no HTML rendering

3.3 TRANSPORT SECURITY
----------------------
- HTTPS only in production (enforce via HSTS header)
- CORS configured for frontend domain only
- Secure cookie flags: httpOnly, secure, sameSite=strict

3.4 DATA PRIVACY
----------------
- Minimal data collection (only what's needed for functionality)
- No tracking or analytics beyond what user explicitly logs
- User can export all their data (GDPR compliance)
- User can delete account and all associated data
- No data sharing with third parties

3.5 ENVIRONMENT SECURITY
------------------------
- Secrets in environment variables (never in code)
- Database credentials rotated periodically
- API keys for OAuth stored securely
- Logging excludes sensitive data (passwords, tokens)

================================================================================

4.1 FIRST-TIME USER (NEW)
-------------------------
1. User opens app -> sees login/register screen
2. User registers with email/password or Google OAuth
3. App creates account with default categories
4. User starts logging hours immediately
5. Data syncs to server automatically

4.2 FIRST-TIME USER (EXISTING LOCAL DATA)
------------------------------------------
1. User opens app -> sees login/register screen
2. App detects localStorage has existing data
3. After login, app prompts: "Migrate existing data?"
4. User confirms -> bulk upload to server
5. localStorage cleared (or kept as cache)
6. App continues normally with server sync

4.3 RETURNING USER
------------------
1. User opens app
2. Token in storage -> auto-login (refresh if needed)
3. Background sync: fetch latest from server
4. User interacts normally
5. Changes sync in background

4.4 OFFLINE USAGE
-----------------
1. User opens app without internet
2. App works normally (localStorage)
3. Changes queued for sync
4. When online, background sync executes
5. Conflicts resolved by timestamp

4.5 MULTI-DEVICE
----------------
1. User logs in on second device
2. Full data pulled from server
3. Both devices sync independently
4. Real-time sync optional (WebSockets, phase 2)

5. EDGE CASES AND ERROR HANDLING
================================================================================

5.1 AUTHENTICATION ERRORS (Google OAuth - MVP)
----------------------------------------------
| Error                  | HTTP Code | User Message                        |
|------------------------|-----------|-------------------------------------|
| OAuth state mismatch   | 400       | "Authentication failed. Try again." |
| Google token invalid   | 401       | "Google sign-in failed. Try again." |
| Google token expired   | 401       | "Google session expired. Try again."|
| JWT token expired      | 401       | (Auto-refresh, if fails -> login)   |
| JWT token invalid      | 401       | "Session expired. Please log in."   |
| Rate limited           | 429       | "Too many attempts. Try again."     |

5.2 DATA VALIDATION ERRORS
--------------------------
| Error                  | HTTP Code | User Message                        |
|------------------------|-----------|-------------------------------------|
| Missing required field | 422       | "{field} is required"               |
| Invalid date format    | 422       | "Date must be YYYY-MM-DD"           |
| Future date            | 422       | "Cannot log hours for future dates" |
| Zero time              | 422       | "Time must be greater than 0"       |
| Name too long          | 422       | "Name must be under X characters"   |
| Duplicate name         | 409       | "A {type} with this name exists"    |

5.3 BUSINESS LOGIC ERRORS
-------------------------
| Error                  | HTTP Code | User Message                        |
|------------------------|-----------|-------------------------------------|
| Category in use        | 409       | "Cannot delete: used in X entries"  |
| Property in use        | 409       | "Cannot delete: used in X entries"  |
| Entry not found        | 404       | "Entry not found"                   |
| Not owner              | 403       | "You don't have access to this"     |

5.4 SYNC CONFLICTS
------------------
Strategy: Last Write Wins
- Compare updatedAt timestamps
- Server version wins if server.updatedAt > local.updatedAt
- Local version wins if local.updatedAt > server.updatedAt
- For deletes: if deleted on server, remove locally (soft delete)

5.5 NETWORK ERRORS
------------------
| Scenario               | Handling                                   |
|------------------------|--------------------------------------------|
| No internet            | Queue changes, retry when online           |
| Server timeout         | Retry with exponential backoff (max 3)     |
| Server 500             | Show error toast, queue for retry          |
| Server unreachable     | Continue offline, sync later               |

IndexedDB Schema (lib/db.ts):
  ```typescript
  import Dexie, { Table } from 'dexie';

  export interface DBEntry {
    id: string;
    date: string;
    hours: number;
    minutes: number;
    totalMinutes: number;
    categoryId: string;
    propertyId: string;
    type: 'material' | 'non-material';
    description: string;
    createdAt: string;
    updatedAt: string;
    syncStatus: 'synced' | 'pending' | 'failed';
  }

  export interface DBCategory {
    id: string;
    name: string;
    color: string;
    createdAt: string;
    updatedAt: string;
    syncStatus: 'synced' | 'pending' | 'failed';
  }

  export interface DBProperty {
    id: string;
    name: string;
    address?: string;
    createdAt: string;
    updatedAt: string;
    syncStatus: 'synced' | 'pending' | 'failed';
  }

  export interface DBSyncQueueItem {
    id?: number;  // auto-increment
    action: 'create' | 'update' | 'delete';
    entityType: 'entry' | 'category' | 'property';
    entityId: string;
    data?: object;
    timestamp: string;
    retryCount: number;
  }

  export class RepsDatabase extends Dexie {
    entries!: Table<DBEntry>;
    categories!: Table<DBCategory>;
    properties!: Table<DBProperty>;
    syncQueue!: Table<DBSyncQueueItem>;

    constructor() {
      super('reps-tracker');
      this.version(1).stores({
        entries: 'id, date, categoryId, propertyId, type, updatedAt, syncStatus',
        categories: 'id, name, syncStatus',
        properties: 'id, name, syncStatus',
        syncQueue: '++id, entityType, entityId, timestamp'
      });
    }
  }

  export const db = new RepsDatabase();
  ```

IndexedDB Benefits:
  - Indexed queries: entries by date range, category, property
  - syncStatus field tracks what needs syncing
  - syncQueue persists offline changes across browser restarts
  - 50MB+ storage vs 5MB localStorage limit
  - Async operations don't block UI

New Pages/Views:
  - Login view (shown when not authenticated)
  - Update app/page.tsx to check auth state before showing app

--------------
Free Tier:
  - Up to 2 properties
  - Up to 5 categories
  - 12 months of history

Pro Tier ($X/month):
